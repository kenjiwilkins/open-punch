指定されたライブラリを**安全に更新する**。ただ上げるのではなく、破壊的変更を事前に把握し、[docs/07-testing.md](../../docs/07-testing.md) のテストスイートで検証してから確定する。

対象: $ARGUMENTS （パッケージ名。第2引数があれば目標バージョン。無ければ最新安定版）

## 手順

1. **現状把握**:
   - `pnpm why <pkg>` と `pnpm ls -r <pkg>` で、現在のバージョンと使用しているワークスペースパッケージを特定。
   - 直接依存か推移的依存かを確認（推移的なら `pnpm.overrides` 等の別手段を検討）。
2. **破壊的変更の調査**:
   - 現在 → 目標バージョンの間の **CHANGELOG / リリースノート / マイグレーションガイド**を WebFetch で確認する。
   - major 更新の場合は特に、破壊的変更（API 変更・削除・デフォルト挙動変更）を箇条書きで洗い出す。
   - 中核ライブラリ（**sst**, **next**, **@pothos/core**, **graphql-yoga**, **aws-sdk**）は影響範囲が広いので慎重に。
   - コード内の該当 API を Grep で洗い、影響箇所をリストアップ。
3. **更新の実行**:
   - 正しいワークスペースパッケージに対して更新する（例: `pnpm --filter <ws> update <pkg>@<version>`）。
   - 破壊的変更でコード修正が必要なら、影響箇所を Edit で最小限に修正する。
4. **検証**（ここを飛ばさない）:
   - `pnpm -r typecheck`
   - `pnpm -r test`（[07-testing.md](../../docs/07-testing.md) の回帰チェックリストが緑であること）
   - 失敗したら原因を調べ、修正するか、更新を見送る判断を提示する。
5. **報告**:
   - 何を何から何へ上げたか、破壊的変更の有無、行ったコード修正、テスト結果をまとめる。
   - `git diff --stat` で変更範囲を提示。

## 注意

- **勝手に commit / push しない**。変更を提示し、確定はオーナーの判断に委ねる。
- テストが緑にならない更新は**確定しない**。壊れたまま進めるくらいなら見送る。
- 1回のコマンドで**1ライブラリ（とその破壊的変更対応）に集中**する。ついでに他も上げない。
